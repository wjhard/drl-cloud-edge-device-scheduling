## 6. OpenHarmony 边界

OpenHarmony 是面向设备/嵌入式的操作系统，不是通用 Linux 服务器运行时。本项目当前是 Python 调度框架，已准备 openEuler/openKylin/Anolis 容器验证；在没有公开、可复验的标准 Python 运行容器或真实 OpenHarmony 设备适配前，不应在 PPT 或答辩中声称“已在 OpenHarmony 原生系统运行”。

建议答辩表述：

> 赛题要求至少基于一种国内主流开源操作系统开发。本项目已经以 openEuler 24.03 LTS-SP4 作为主要验证环境，并额外完成 openKylin 2.0 SP1 与 Anolis OS 23 Docker 验证矩阵。OpenHarmony 更偏设备端运行时，本项目目前不夸大为原生 OpenHarmony 部署。

## 7. 30～60 任务扩展、统一 CLI 与资源开销（2026-09-05）

### 7.1 容量安全修复

最终 Residual checkpoint 的输入容量为 30。旧入口会在 40～60 任务时先创建
Residual 环境，尚未进入 HEFT 安全候选就因观测容量不匹配而失败。本轮将完整
Adaptive 调度器改为：

- `task_count <= 30`：正常执行 Residual sampling、合法重定位、LNS 与启发式候选；
- `task_count > 30`：显式跳过越界神经网络，记录 `residual_skipped_reason`，执行
  HEFT 锚点和 best-only LNS；
- 任意规模最终均从合法候选中按 makespan 取最优，保持相对 HEFT 非回归；
- rollout、重定位和 LNS 新增软墙钟截止检查，已经开始的单次评估与 HEFT 锚点
  允许完成，确保不会因超时返回半成品调度。

### 7.2 大规模正式结果

固定场景：`evaluation/scenarios_large/`，30/40/50/60 任务各 5 个。

| 协议 | mean_ratio ± 样本标准差 | 反超 HEFT | p（双侧） | 平均墙钟时间 | P95 | 峰值 RSS |
|---|---:|---:|---:|---:|---:|---:|
| 64/3/64，每场景 10 秒软预算 | 0.941627 ± 0.026569 | 20/20 | 6.985758×10^-9 | 10.002 秒 | 10.003 秒 | 358.1 MiB |

### 7.3 评委可直接运行的接口

新增 `scripts/schedule.py`，输入一个 DAG JSON，输出：

- 每个任务的资源、开始时间、结束时间和持续时间；
- makespan、HEFT makespan 与比值；
- 模型加载、调度、HEFT 参考耗时及进程内存；
- 候选来源、模型容量降级原因、时间预算状态；
- 完整性、资源互斥和带通信时间的 DAG 前驱约束校验。

示例：

```bash
python scripts/schedule.py --input evaluation/scenarios/scenario_10_0.json \
  --output evaluation/results/schedule_output.json --preset balanced \
  --time-budget-seconds 10
```
